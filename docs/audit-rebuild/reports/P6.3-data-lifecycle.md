# P6.3 Data Lifecycle

Captured: 2026-07-12 PDT

State: `EVIDENCE_READY`

Evidence ID: `EV-P6-LIFE-003`.

## Current Lifecycle Risks

- Schema version is overwritten to v2 during normalization; no migration registry,
  compatibility check, quarantine, or rollback exists.
- Import immediately normalizes/persists/pushes with no preview, dry run, backup,
  duplicate report, or transaction.
- Every mutation recalculates historical model-derived values.
- Explicit delete removes image binaries before committing the ledger tombstone;
  clear removes all images before committing all tombstones.
- Attachment keys sync but binary bytes do not.
- Tombstones have no retention/compaction policy.
- The full dataset must remain below an application-imposed 1 MiB request cap; the
  500-trade fixture is already 335,966 bytes before real long notes/media metadata.
- Export has no completeness manifest for missing attachments or unsynced mutations.

This opens `F-DATA-HIGH-003` for cosmetic schema versioning and
`F-DATA-HIGH-004` for non-transactional media deletion.

## Target Lifecycle

`validate -> preview -> snapshot backup -> migrate in transaction -> invariant check
-> commit -> enqueue sync -> retain rollback marker`.

Exports include schema, app, model, authoritative revision, records, settings,
tombstones in retention, attachment manifest/hashes, and pending-mutation manifest.
Import reports adds/updates/conflicts/rejections before commit. Attachments use
content hashes and two-phase deletion: tombstone first, remote acknowledgement and
retention window second, binary garbage collection last.
