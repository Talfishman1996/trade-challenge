# P1.6 Standards and Reference Baseline

Accessed: 2026-07-12 PDT

Scope: current primary/authoritative sources used to interpret later evidence. This
index separates normative requirements, platform behavior, provider constraints,
and project quality preferences.

## Accessibility

### Normative baseline

- [WCAG 2.2](https://www.w3.org/TR/WCAG22/) is the normative W3C Recommendation.
  Relevant AA criteria include 4.5:1 normal-text / 3:1 large-text contrast, text
  resize to 200% without loss, reflow, focus not obscured, labels/instructions,
  keyboard use, and name/role/value.
- [WCAG 2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)
  defines a 24x24 CSS-pixel AA minimum with spacing/equivalent/inline/user-agent/
  essential exceptions. The audit program's 44 px target is a stricter mobile
  usability quality budget, not the WCAG 2.5.8 normative threshold.
- [WCAG Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum)
  and [Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow) are directly
  relevant to the fixed bottom navigation, fixed trade sheet, horizontal History
  table, keyboard-open state, and 200% text state.
- [WAI Labeling Controls](https://www.w3.org/WAI/tutorials/forms/labels/) says all
  form controls need properly associated labels and explains explicit `for`/`id`,
  implicit labels, and accessible alternatives.
- [WAI Accessible Names and Descriptions](https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/)
  states that focusable interactive elements require effective accessible names and
  favors native HTML naming where possible.

### Audit consequence

The P1 geometry scan cannot declare a WCAG failure merely because a control is under
44 px. P8 must evaluate the 24 px rule and spacing exceptions separately while still
enforcing the project's higher one-handed mobile target. Missing names, unassociated
controls, contrast, focus obstruction, reflow, and text resizing remain standards
questions, not aesthetic preferences.

## Mobile Browser Behavior

- WebKit's [safe-area guidance](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)
  explains that `viewport-fit=cover` makes content responsible for all four
  `safe-area-inset-*` values, including landscape side insets, and recommends
  combining insets with minimum padding.
- Chrome's official [virtual-keyboard viewport guidance](https://developer.chrome.com/blog/viewport-resize-behavior/)
  documents Layout versus Visual Viewports, fixed-element obstruction, and the
  default `resizes-visual` behavior in Chrome 108+.
- WebKit's [Safari 26 feature record](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
  is the dated current-platform reference; physical Safari validation is still
  required because emulated Chromium does not prove WebKit behavior.

### Audit consequence

The app opts into `viewport-fit=cover` but only defines a bottom safe-area utility.
Its fixed navigation, floating sync button, and fixed 90vh entry sheet require
physical portrait/landscape and keyboard proof. A desktop/emulated viewport that
shows no overflow cannot close those requirements.

## Performance and Framework

- Google's [Core Web Vitals threshold methodology](https://web.dev/articles/defining-core-web-vitals-thresholds)
  defines good p75 field thresholds of LCP <=2.5 s, INP <=200 ms, and CLS <=0.1.
  Local single-run paint values are not equivalent to field p75 evidence.
- React's current [StrictMode reference](https://react.dev/reference/react/StrictMode)
  confirms that development re-runs Effects an extra time. This explains two audit
  boot requests without excusing non-idempotent effects or production races.
- Vite's [build options](https://vite.dev/config/build-options.html) set the default
  chunk warning at 500 kB uncompressed and copy `publicDir` into output by default.
- Vite's [production build guide](https://vite.dev/guide/build) documents dynamic
  import chunking and `vite:preloadError`, relevant to lazy-view recovery.

### Audit consequence

P1 local LCP/CLS values are instrumentation smoke tests only. P8 must use repeatable
production builds and physical/representative devices. Vite's public-copy behavior
explains why both unused monument files ship, but does not make that cost desirable.

## Cloudflare Hosting and Sync

- [Workers KV limits](https://developers.cloudflare.com/kv/platform/limits/) were
  updated 2026-04-21: Free allows 100,000 reads/day, 1,000 writes/day to different
  keys, but every plan permits only one write per second to the same key; values can
  be 25 MiB.
- [How KV works](https://developers.cloudflare.com/kv/concepts/how-kv-works/) says KV
  is eventually consistent, changes can take 60 seconds or more to appear elsewhere,
  and KV is not appropriate for atomic read/write transactions. Cloudflare points to
  Durable Objects when stronger consistency is required.
- [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) were
  updated 2026-07-05: Free has 100,000 requests/day and 128 MB memory.
- [Pages limits](https://developers.cloudflare.com/pages/platform/limits/) were
  updated 2026-07-05: Free allows 500 builds/month, 20,000 files, and 25 MiB per
  asset. The current build is within those static-hosting limits.

### Audit consequence

The current architecture writes every device to one key, can launch overlapping
writes during save/autosave, polls independently, and assumes a fresh read can
confirm the preceding write. KV's one-write-per-second limit, cross-location stale
reads, and lack of transactionality invalidate that assumption. This is independent
of whether the account stays within free daily quotas.

## Browser Storage

- MDN's authoritative [Web Storage overview](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API)
  documents that localStorage is synchronous and can block JavaScript when data is
  substantial; it is origin-scoped and behaves differently in private browsing.
- MDN's [localStorage reference](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)
  records policy/security exceptions and protocol-specific origin separation.
- MDN's [IndexedDB guide](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB)
  describes asynchronous persistent browser storage and explicit version/lifecycle
  handling.
- MDN's [Storage API overview](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API)
  explains that an origin's best-effort data can be evicted and that persistent
  storage must be requested; clearing an origin can remove its storage bucket.
- MDN's [quota/eviction reference](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
  documents browser-specific quotas and eviction behavior.

### Audit consequence

"Saved locally" is not an unconditional durability guarantee. The product needs an
explicit local/cloud/pending contract, quota/error handling, image lifecycle, and
cross-origin/domain migration plan. IndexedDB does not sync itself; the application
must transfer attachment bytes deliberately.

## Requirement Classification

| Class | Examples |
|---|---|
| Normative | WCAG contrast, resize, reflow, focus, labels, names, target minimum |
| Platform behavior | safe areas, visual viewport/keyboard, origin storage, eviction |
| Provider constraint | KV consistency/write rate, Worker/Page quotas and file limits |
| Framework behavior | React development effect replay, Vite public copying/chunk warning |
| Project quality budget | 44 px frequent touch targets, mobile-only primary optimization, no silent sync uncertainty |

Later phases must cite the correct class. A preference cannot be presented as a
standard, and a provider consistency limit cannot be dismissed as a design opinion.

## Verification Result

The required iOS/WebKit, Android/Chrome, WCAG/WAI, Web Vitals, React, Vite,
Cloudflare Pages/Workers/KV, and browser-storage domains each have a dated primary or
authoritative source. `EV-P1-SRC-004` is evidence-ready as of the access date above.
